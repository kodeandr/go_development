# Cashcraft: бюджеты и расходы

Проект по теме «Базы данных»: PostgreSQL хранит бюджеты и расходы, Redis кеширует
сводные отчёты на 30 секунд. В репозитории два Go-модуля — `gateway` и `ledger`,
объединённые файлом `go.work`. В `gateway/go.mod` также есть локальный `replace`,
поэтому Gateway можно собирать отдельно от workspace.

Gateway импортирует пакет Ledger и вызывает его методы напрямую — это способ
связи из ДЗ №5. HTTP-контракт остаётся прежним: бюджет содержит поле `limit`.
SQL-колонка называется `limit_amount`; её имя не попадает в публичный API.

При запуске Gateway создаёт свой экземпляр Ledger с подключениями к PostgreSQL
и Redis. Отдельная команда Ledger проверяет подключения, позволяет загрузить
бюджеты из файла и обслуживает `/healthz` на порту 8081. Между этими процессами
нет HTTP-проксирования: источником общих данных служит PostgreSQL. HTTP-операции
с бюджетами, расходами и отчётами доступны только через Gateway на порту 8080.

## Быстрый запуск

Нужны Go 1.23 или новее, Docker с Compose v2 и `make`. Для сквозного сценария
дополнительно нужен Python 3. Команды выполняются из корня репозитория.

```bash
cp .env.example .env
set -a
. ./.env
set +a
make deps
make tools
make up
make migrate-up
```

`make tools` устанавливает Goose v3.24.3 в `.bin/goose` с драйвером PostgreSQL.
`make up` дожидается успешных healthcheck PostgreSQL 16 и Redis 7. Миграции
применяются **до** запуска приложений.

Первый терминал:

```bash
set -a; . ./.env; set +a
make run-ledger
```

Второй терминал, также из корня репозитория:

```bash
set -a; . ./.env; set +a
make run-gateway
```

Успешные подключения журналируются: `connected to PostgreSQL` и
`connected to Redis`. При недоступных зависимостях или отсутствии миграций
приложение завершится с понятной ошибкой и ненулевым кодом.

```bash
curl -i http://localhost:8080/ping
# 200, тело: pong
curl -i http://localhost:8080/healthz
# 200, тело: {"status":"ok"}
```

Независимый запуск модулей: `cd ledger && go run ./cmd/ledger` и
`cd gateway && go run .`. Оба процесса должны получить одинаковые настройки
подключений. Go не загружает `.env` автоматически.

## Миграции

В `ledger/migrations/` два файла Goose с секциями `Up` и `Down`:
таблицы `budgets`, `expenses` и индекс `(category, date)`.

```bash
.bin/goose -dir ./ledger/migrations postgres "$DATABASE_URL" up
.bin/goose -dir ./ledger/migrations postgres "$DATABASE_URL" status
.bin/goose -dir ./ledger/migrations postgres "$DATABASE_URL" down
```

`down` откатывает одну миграцию: сначала удаляет `expenses`, повторный вызов —
`budgets`. При откате данные удаляемой таблицы теряются. Миграции запускаются
отдельно, а не при каждом старте приложения.

## HTTP API

| Метод | Путь | Результат |
| --- | --- | --- |
| POST | `/api/budgets` | Создание или обновление бюджета, 201 |
| GET | `/api/budgets` | Бюджеты по категориям, 200 |
| POST | `/api/transactions` | Новый расход, 201; превышение бюджета — 409 |
| GET | `/api/transactions` | Расходы по `date DESC, id DESC`, 200 |
| GET | `/api/reports/summary?from=YYYY-MM-DD&to=YYYY-MM-DD` | Отчёт за включительный период, 200 |

```bash
curl -i -X POST http://localhost:8080/api/budgets \
  -H 'Content-Type: application/json' \
  -d '{"category":"Продукты","limit":5000.00}'
curl -i -X POST http://localhost:8080/api/transactions \
  -H 'Content-Type: application/json' \
  -d '{"amount":1250.50,"category":"Продукты","description":"Покупка в магазине","date":"2026-01-15"}'
curl -sS http://localhost:8080/api/transactions
```

Ошибки API имеют формат `{"error":"..."}`: 400 — валидация или неверный JSON,
409 — `budget exceeded`, 500 — внутренняя ошибка. Ответы API, включая 404/405,
имеют `Content-Type: application/json; charset=utf-8`. Для старого проверочного
маршрута `/ping` сохранено текстовое тело `pong`. Middleware журналирует метод,
путь и длительность каждого запроса.

Полная последовательность cURL, включая превышение лимита и два запроса
отчёта, — в [gateway/README.md](gateway/README.md).

## Правила и хранение

- `Transaction` и `Budget` реализуют `Validatable`. Методы `Validate` возвращают
  ошибки и не пишут в журнал; функция `CheckValid` работает с обоими типами.
- Расход должен быть положительным. Нулевые и отрицательные суммы отклоняются,
  как требуется в ДЗ №4 и №6. SQL-проверка `amount <> 0` оставлена по схеме ДЗ №7;
  прикладная валидация намеренно строже ограничения таблицы.
- Категория обязательна, дата расхода — корректная `YYYY-MM-DD`. Лимит бюджета
  положительный. В JSON деньги передаются числами с точкой и не более чем двумя
  дробными знаками, без экспоненциальной записи.
- Деньги хранятся в Go целым количеством копеек, в БД — `NUMERIC(14,2)`.
  Погрешностей вычислений через `float64` нет.
- Повторная запись бюджета выполняет UPSERT. Без бюджета расходы разрешены.
  При наличии бюджета сумма всех расходов категории вместе с новым расходом
  не должна превышать лимит. Равенство разрешено, бюджет не привязан к месяцу.
- Проверка лимита и INSERT идут в одной SQL-транзакции. Изменение бюджета и
  добавление расхода используют одну advisory-блокировку категории, защищая
  лимит от параллельных запросов.
- Отчёт кешируется в Redis на 30 секунд. В журнале видны `cache=miss` и
  `cache=hit`. После записи расхода меняется версия ключей отчётов. Списки
  бюджетов не кешируются: это необязательная часть задания.

При отказе Redis во время работы отчёт читается из PostgreSQL. Сохранённый
расход не превращается в ошибку из-за неудачной инвалидации кеша; в таком случае
старый отчёт может оставаться доступным до истечения TTL.

Настройки `DATABASE_URL`, `DB_*`, `REDIS_*`, пул 10 open / 5 idle и загрузка
бюджетов через `io.Reader` описаны в [ledger/README.md](ledger/README.md).

## Тесты и покрытие

```bash
make build
make test
make coverage
```

Unit-тесты табличные, с `t.Run`; независимые проверки помечены `t.Parallel`.
`make test` включает `-race` и `go vet`. Для `-race` нужен C-компилятор.
`make coverage` создаёт `cover.out`, `cover.html` и печатает процент покрытия.

Измеренное покрытие всех Go-пакетов: **43,0%** для unit-тестов и **76,1%**
для полного набора с PostgreSQL/Redis (`make coverage-integration`). Валидация
Transaction, Budget и периодов покрыта на 100%. Запуск отдельных процессов
дополнительно проверяется сквозным сценарием и не входит в этот процент.

Интеграционные тесты работают с настоящими PostgreSQL и Redis:

```bash
make up
make tools
TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/cashapp?sslmode=disable' \
  make integration
TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/cashapp?sslmode=disable' \
  make coverage-integration
```

Тесты создают и удаляют отдельные схемы PostgreSQL; роли нужно право
`CREATE SCHEMA`. Для Redis используется БД 15 с уникальными префиксами,
без `FLUSHDB`. Для другой установки задайте `TEST_REDIS_ADDR` и при необходимости
`TEST_REDIS_PASSWORD`. Очистка выполняется через `t.Cleanup`, функция `Reset`
для общей базы не используется.

Проверяются SQL-ограничения, up/down, UPSERT, положительные суммы, достижение
лимита, отказ без вставки, конкурентные расходы, повторное подключение,
импорт JSON, cache hit/miss, TTL, инвалидация и отказ Redis. HTTP-тесты проходят
полную цепочку POST бюджета → POST расхода → GET → 409 через настоящий Ledger,
а также проверяют DTO, заголовки и ошибки.

```bash
make migrate-up
make smoke
```

Сквозной сценарий сам запускает бинарные файлы на свободных локальных портах,
выполняет запросы через Gateway, перезапускает отдельный Ledger, затем Gateway
вместе с его экземпляром Ledger, и сравнивает сохранённые данные. После проверки
оба процесса останавливаются. В учебной БД остаётся бюджет и два расхода
с уникальной категорией `smoke-...`, имя выводится в консоль. Redis для сценария
используется в БД 15 (переопределяется через `SMOKE_REDIS_DB`). Не запускайте
сценарий на рабочей БД или одновременно с другими записывающими клиентами.

Связь требований предыдущих тем с текущей реализацией приведена в
[docs/requirements.md](docs/requirements.md).

## Остановка

`Ctrl+C` или `SIGTERM` корректно завершает HTTP-сервер и закрывает подключения.
`make down` останавливает контейнеры, сохраняя PostgreSQL в именованном volume.
`docker compose down -v` также удалит volume и все данные учебной БД.
